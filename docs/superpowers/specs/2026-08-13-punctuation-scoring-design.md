# Слова с пунктуацией внутри и коррекция по Enter — Дизайн-документ

**Дата:** 2026-08-13
**Статус:** утверждён

## 1. Цель

Исправить два независимых дефекта, из-за которых слово, содержащее пунктуацию (характерный случай — доменное имя вида `amazon.de`), не корректируется:

1. **Детектор не срабатывает.** Символ, который в целевой раскладке является пунктуацией, а в набранной — буквой, участвует в скоринге как обычная буква и смещает скоры за пороги.
2. **Коррекция по Enter опаздывает.** `correctionDelay = 0.05` откладывает замену на 50 мс; за это время браузер уже отправил запрос по неправильному адресу.

Исходный сценарий пользователя: в адресной строке браузера при активной русской раскладке набрано `фьфящтюву` (это `amazon.de`), нажат Enter — коррекции не происходит.

## 2. Диагностика (root cause)

### 2.1 Скоринг

Клавиша `.` в русской раскладке даёт «ю» — полноценную кириллическую букву. `LanguageDetector.isWrongLayout` скорит слово целиком, поэтому «ю» попадает и в подсчёт гласных, и в частотную сумму.

Для `фьфящтюву` (активна русская раскладка, вариант `.pc`):

| | оригинал | converted | `russianScore` | `englishScore` | `russian < 0.4` |
|---|---|---|---|---|---|
| сейчас | фьфящт**ю**ву | amazon**.**de | **0.424** | 0.638 | ✗ — коррекция отменяется |

`russianThreshold = 0.4`, а скор равен `0.424`. «ю» — гласная (`vowelCount` 2 → 3 из 9, `vowelRatio` ближе к целевым 0.4) и добавляет частотный вес `0.05`. Ровно она и удерживает скор над порогом.

Убрав «ю» из подсчёта (но не из слова), получаем `russianScore(фьфящтву) = 0.323` — все три условия выполняются.

Симметричный случай `.` → «ю» действует и для остальных клавиш из `TextConverter.ambiguousLetterSymbols`: `,` → «б», `;` → «ж», `'` → «э», `[` → «х», `]` → «ъ».

### 2.2 Enter

`InputMonitor.handle` на границе слова планирует `applyCorrection` через `correctionDelay`. Задержка существует для видимых разделителей: приложение должно успеть напечатать пробел или запятую до того, как мы перепишем текст.

Для Enter это ограничение неприменимо — Enter не печатает видимого символа. Зато он немедленно запускает действие приложения (навигация, отправка формы), и 50 мс спустя править уже нечего.

При этом event tap создан с `place: .headInsertEventTap` — наш callback вызывается **до** доставки события приложению. Работа, выполненная синхронно внутри callback'а, приложением будет увидена.

## 3. Требования

- Слово с пунктуацией внутри (`amazon.de`, `google.com`, `t.me`) должно детектироваться и заменяться **целиком**, вместе с пунктуацией.
- Разбиение такого слова на части по пунктуации недопустимо: `фьфящтюву` распалось бы на `фьфящт` → `amazon` и `ву` → `de`, а `ву` короче `minWordLength = 3` и осталось бы неисправленным (`amazon.ву`).
- Слова, где неоднозначный символ — настоящая буква конечного текста («пою» = `gj.`, «уж» = `e;`, «объект» = `j,]trn`), не должны получить регрессию.
- Коррекция по Enter должна успевать до того, как приложение обработает Enter — в приложениях с рабочим AX (браузеры, поля ввода, текстовые редакторы).
- `LanguageDetector` и `TextConverter` остаются чистыми функциями без системных зависимостей.
- Режим event tap не меняется (`options: .listenOnly`), синтетический Enter не отправляется.

## 4. Архитектура

### 4.1 `LanguageDetector` — фильтрация позиций перед скорингом

`isWrongLayout` перед вычислением скоров выбрасывает из **обеих** строк те позиции, где символ в `converted` является пунктуацией или символом. Конверсия в `TextConverter.convert` посимвольная 1:1, поэтому индексы оригинала и конверсии строго соответствуют друг другу.

```swift
/// Позиции, где конверсия даёт пунктуацию, — это разделители, попавшие
/// внутрь слова, а не его буквы. Они искажают и долю гласных, и частотную
/// сумму, поэтому выбрасываются из обеих строк перед скорингом. Само слово
/// при этом заменяется целиком, вместе с пунктуацией.
private static func strippingPunctuation(
    _ original: String, _ converted: String
) -> (original: String, converted: String) {
    let originalChars = Array(original)
    let convertedChars = Array(converted)
    guard originalChars.count == convertedChars.count else { return (original, converted) }

    var keptOriginal = ""
    var keptConverted = ""
    for (o, c) in zip(originalChars, convertedChars) where !(c.isPunctuation || c.isSymbol) {
        keptOriginal.append(o)
        keptConverted.append(c)
    }
    return (keptOriginal, keptConverted)
}
```

Точка встраивания — после проверки исключений, перед скорингом:

```swift
if exceptions.contains(converted) { return true }

let (scoredOriginal, scoredConverted) = strippingPunctuation(lower, converted)

if currentLayoutIsRussian {
    let russian = russianScore(scoredOriginal)
    let english = englishScore(scoredConverted)
    ...
```

Не меняется:

- `minWordLength` и `allSatisfy` проверяются на **полном** слове, до фильтрации;
- `exceptions` сверяются с **полным** словом и **полной** конверсией;
- заменяется в тексте **полное** слово — фильтрация касается только скоринга.

Защита `originalChars.count == convertedChars.count` — страховка на случай, если конверсия когда-нибудь перестанет быть 1:1 (например, маппинг в диграф). При расхождении длин фильтрация пропускается и поведение откатывается к текущему.

Если после фильтрации строки пусты, оба скора равны 0, условие `english > englishThreshold` не выполняется, коррекции не происходит — деградация безопасная.

### 4.2 Асимметрия: фильтруем по `converted`, не по оригиналу

Фильтр смотрит только на конверсию. Символ, который является пунктуацией в **оригинале**, но буквой в конверсии, в скоринге остаётся.

Обоснование — направление набора. При активной **английской** раскладке пользователь, который печатает по-русски, ставит русскую запятую через Shift+`/` (в PC-варианте), что даёт на экране `?` — обычную границу слова. Нажатие же клавиши `,` в этом состоянии означает ровно намерение набрать «б». Поэтому `ghbdtn,` → «приветб» — корректная интерпретация, и она не меняется.

При активной **русской** раскладке зеркальная ситуация: пользователь, печатающий по-английски, жмёт `.` и получает «ю» — букву в оригинале, пунктуацию в конверсии. Это и есть случай, который фильтр обязан покрыть.

### 4.3 `InputMonitor` — синхронная коррекция на Enter и Tab

В ветке границы слова разделители `isNewline` и `\t` обрабатываются немедленно, минуя `correctionDelay`:

```swift
} else if isWordBoundary(char) {
    if currentWord.isEmpty {
        scheduleLeadingCharCheck(char)
    } else if LanguageDetector.isWrongLayout(...) {
        if char.isNewline || char == "\t" {
            // Enter/Tab не печатают видимого символа, поэтому ждать нечего —
            // а ждать вредно: приложение выполнит действие (навигация,
            // отправка формы) раньше, чем сработает отложенная замена.
            // Наш tap стоит в .headInsertEventTap, так что работа, сделанная
            // здесь синхронно, будет видна приложению до обработки клавиши.
            applyCorrectionNow(word: currentWord, ...)
        } else {
            scheduleRetroactiveCheck(...)
        }
    }
    currentWord = ""
}
```

`applyCorrectionNow` — тонкая обёртка: `captureWordAnchor` (уже выполняется синхронно и сегодня) плюс немедленный вызов существующего `applyCorrection` с тем же набором аргументов, что и у отложенного пути.

Сам `applyCorrection` **не меняется**. Его существующий guard уже возвращает `false` для `boundary.isNewline` и `boundary == "\t"` перед keystroke-fallback'ом, поэтому синхронный путь остаётся AX-only — синтетические клавиши в терминал не отправляются, обоснование прежнее (см. `2026-08-12-terminal-keystroke-fallback-design.md`).

Порядок «замена → переключение раскладки» сохраняется без изменений.

Для всех остальных разделителей (пробел, пунктуация, цифра, символ) `correctionDelay = 0.05` остаётся: там разделитель печатает видимый символ, и приложению нужно дать его обработать до замены.

### 4.4 `InputMonitor` — пере-включение tap после отключения системой

Синхронные AX-вызовы внутри callback'а увеличивают время его выполнения, а значит и риск, что система отключит tap за превышение таймаута. Сегодня `handle` молча отбрасывает всё, кроме `.keyDown`, поэтому такое отключение приведёт к тихой смерти приложения до перезапуска.

Первой строкой `handle` добавляется:

```swift
if type == .tapDisabledByTimeout || type == .tapDisabledByUserInput {
    if let eventTap { CGEvent.tapEnable(tap: eventTap, enable: true) }
    return
}
```

Эти два типа событий доставляются в callback независимо от `eventsOfInterest`, поэтому маска не меняется.

## 5. Поток данных

Изменённые участки выделены **жирным**.

```
CGEventTap (.headInsertEventTap, .listenOnly)
  └─ handle(event:type:)
       ├─ **tapDisabled* → tapEnable(true), выход**
       ├─ буква / неоднозначный символ → буфер растёт
       └─ граница слова
            └─ LanguageDetector.isWrongLayout
                 └─ **strippingPunctuation(original, converted)** → скоринг
            ├─ **Enter / Tab → applyCorrectionNow (синхронно, AX-only)**
            └─ прочие → scheduleRetroactiveCheck (correctionDelay 0.05)
```

## 6. Тестирование

### 6.1 Юнит-тесты (`LanguageDetectorTests`)

Целевой случай — сейчас не срабатывает, после фикса должно:

| Слово | Раскладка | Конверсия | `russianScore` до → после |
|---|---|---|---|
| `фьфящтюву` | русская, `.pc` | `amazon.de` | 0.424 → 0.323 |

Домены, которые срабатывают уже сейчас, — тест на отсутствие регрессии от фильтрации (укорачивание слова не должно уводить скоры за пороги):

| Слово | Раскладка | Конверсия |
|---|---|---|
| `пщщпдуюсщь` | русская, `.pc` | `google.com` |
| `еюьу` | русская, `.pc` | `t.me` |

Регрессии — не должно срабатывать:

| Слово | Раскладка | Конверсия | Почему |
|---|---|---|---|
| `пою` | русская | `gj.` | «ю» — настоящая буква слова |
| `мою` | русская | `vj.` | то же |
| `объём` | русская, `.pc` | ``j,]`v`` | три отфильтрованные позиции подряд |
| `съел` | русская | `c]tk` | «ъ» на клавише `]` |
| `т.е.` | русская, `.pc` | `n/t/` | корректное русское сокращение |
| `т.к.` | русская, `.pc` | `n/r` | то же |
| `ghbdtn,` | английская | `приветб` | `,` при английской раскладке = «б», поведение прежнее |
| `j,]trn` | английская | `объект` | пунктуация только в оригинале, фильтр не применяется |
| `[jxe` | английская | `хочу` | то же |

Варианты раскладки: `объём` и `т.е.` проверяются для `.pc` и `.apple` отдельно — «ё» и `.` расшифровываются в них по-разному.

Отдельный тест на страховку: при расхождении длин оригинала и конверсии фильтрация не применяется.

### 6.2 Ручная проверка

`InputMonitor` — тонкая обёртка над системными API, юнит-тестами не покрывается:

- адресная строка Safari и Chrome: `фьфящтюву` + Enter → переход на `amazon.de` с первого раза;
- поле поиска на странице: слово + Enter;
- TextEdit и Notes: слово + Enter (перевод строки), слово + Tab;
- поле ввода в мессенджере: убедиться, что отправляется ровно одно сообщение;
- Terminal.app: поведение по Enter не изменилось (коррекции нет);
- длительная сессия набора: tap не отключается, а при отключении — восстанавливается.

## 7. Вне области

- **Enter в терминале.** Коррекция там идёт синтетическими клавишами, которые встанут в очередь после уже отправленного Enter. Требует перевода tap в активный режим с подавлением клавиши — отклонено: риск задержки всего ввода и отключения tap'а по таймауту не оправдан.
- **Конверсия самого разделителя.** При активной английской раскладке русская запятая приходит как `?`, точка — как `/`; слово исправляется, разделитель остаётся латинским. Маппинга `?` → `,` в `TextConverter` вообще нет. Отдельная задача.
- **`ghbdtn,` → «приветб».** Не дефект, см. 4.2.
- **Пороги эвристики** (`russianThreshold` и прочие) не трогаются: фильтрация меняет вход скоринга, а не его калибровку.
