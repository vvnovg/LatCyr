# Заглавные Б, Ю, Ж, Э, Х, Ъ: символы с Shift на клавишах русских букв

## Проблема

Шесть русских букв стоят на пунктуационных клавишах английской раскладки: Б на `,`, Ю на `.`, Ж на `;`, Э на `'`, Х на `[`, Ъ на `]`. Строчные `TextConverter` знает, заглавные — нет. С Shift эти клавиши дают `<` `>` `:` `"` `{` `}`, и в таблице их нет. Ё на `~` (Russian – PC) и `|` (Russian) уже есть.

Последствия:

- **Русская раскладка → английский текст:** буфер собирает «Б», «Ж» как буквы, но конверсия идёт через строчную пару и Shift теряется. `БвшмЮ` превращается в `,div.` вместо `<div>`, а `цщкдвЖ` — в `world;` вместо `world:`.
- **Английская раскладка → русский текст:** `<` `>` `:` `"` `{` `}` считаются границей слова и рвут буфер. «Это» в начале фразы, набранное как `"nj`, не исправляется вовсе: до детектора доходит `nj`, которое короче `minWordLength`. «Хорошо» (`{jhjij`) превращается в `{` + исправленное «орошо».
- **Ручное исправление ⇧⇧** (`ManualFix.plan`): `<s` не конвертируется, `"nj` даёт `"то`.

## Решение

### 1. Таблица `TextConverter`

В общую таблицу `sharedLatinToCyrillic` добавляются шесть пар:

| Латиница | Кириллица |
|---|---|
| `<` | Б |
| `>` | Ю |
| `:` | Ж |
| `"` | Э |
| `{` | Х |
| `}` | Ъ |

Пары общие для `.pc` и `.apple`: эти клавиши у вариантов совпадают (спека вариантов раскладки, 2026-08-13). Обратная таблица строится инверсией, как сейчас, поэтому «Б» → `<`, а «б» по-прежнему → `,`. В `convert` точное совпадение проверяется раньше пути через нижний регистр, так что заглавные получают свою пару, а не строчную с поднятым регистром.

### 2. Буфер слова: новые символы — «неоднозначные»

`TextConverter.ambiguousLetterSymbols(for:)` дополняется:
- для обоих вариантов — `<` `>` `:` `"` `{` `}`;
- для `.pc` — `~` (Ё);
- для `.apple` — `|` (Ё).

Эта функция — единый источник для трёх мест, которые по CLAUDE.md обязаны видеть один и тот же набор: накопление буфера в `InputMonitor.handle`, поиск слова на экране `TextFieldController.isBoundary` и проверка «только буквы и неоднозначные символы» в `LanguageDetector.isScorable`. Расширение одной функции держит их согласованными.

### 3. Выбор прочтения токена — `LanguageDetector.wrongLayoutReading`

Новая чистая функция:

```swift
public struct Reading: Equatable {
    public let prefix: String   // ведущий символ-пунктуация, не конвертируется
    public let core: String     // конвертируемая часть
    public let suffix: String   // хвостовая пунктуация, не конвертируется
}

public static func wrongLayoutReading(
    token: String, currentLayoutIsRussian: Bool,
    exceptions: Set<String>, variant: TextConverter.RussianKeyboardVariant
) -> Reading?
```

Правила:

1. **Хвост.** Сплошная серия символов из набора `shiftedLetterSymbols` в конце токена — всегда пунктуация: `suffix`. Слов, оканчивающихся заглавной буквой, практически нет, а `word:`, `слово"`, `}` в конце — обычное дело.
2. **Начало.** Если оставшаяся часть начинается с символа из набора `shiftedLetterSymbols` и длиннее одного символа, проверяются два прочтения:
   - **A** — символ буква: `prefix = ""`, `core` = вся часть;
   - **B** — символ пунктуация: `prefix` = этот символ, `core` = остальное.

   Иначе прочтение одно — A.
3. **Выбор.** Для каждого прочтения: `isWrongLayout(core)` и `wrongLayoutLLR(core)`. Среди прочтений, признанных чужой раскладкой, выбирается то, у которого LLR выше. Слово-исключение или домен в конверсии (их признаёт `isWrongLayout` до скоринга) считаются бесспорными и выигрывают у любого LLR. Если ни одно прочтение не признано ошибкой — `nil`.
4. Символы в середине токена остаются буквами — как сейчас `;` в `ckj;yj` («сложно»).

`shiftedLetterSymbols(for:)` — новая публичная функция `TextConverter`: подмножество `ambiguousLetterSymbols` из символов с Shift (`<` `>` `:` `"` `{` `}`, плюс `~` для `.pc` или `|` для `.apple`). Только они участвуют в правилах 1–2. Строчные `,` `.` `;` `'` `[` `]` и `` ` ``/`\` правила не меняют: их обработка остаётся прежней.

Примеры (английская раскладка, слово уходит в русский):

| Набрано | Прочтение | Результат |
|---|---|---|
| `"nj` | A | «Это» |
| `{jhjij` | A | «Хорошо» |
| `:fkm` | A | «Жаль» |
| `ghbdtn:` | хвост | «привет:» |
| `"ghbdtn"` | B + хвост | `"привет"` — «Эпривет» как русское слово неправдоподобно |
| `"hello"` | — | не трогается |
| `foo:bar` | — | не трогается |

Русская раскладка, слово уходит в английский: «Б», «Ж» и т.д. там буквы, правила 1–2 их не касаются, а конверсия идёт по новой таблице: `цщкдвЖ` → `world:`, `БвшмЮ` → `<div>`. Настоящие `:` и `"` в русской раскладке (Shift+6, Shift+2 у Russian – PC) попадают в хвост и сохраняются.

### 4. `InputMonitor`

На границе слова `wrong` вычисляется через `wrongLayoutReading(currentWord, ...)` вместо `isWrongLayout(currentWord, ...)`, по-прежнему `|| isTerminalCommand()`.

Заменяется весь токен, как он стоит на экране: якорь (`captureWordAnchor`), сверка текста, число Backspace keystroke-fallback'а считаются по `currentWord`, как сейчас. Меняется только текст замены: `prefix + конверсия(core) + suffix`. Для этого `applyCorrection` получает готовую конверсию слова параметром (`convertedWord`), а не вычисляет её из `word`. Конверсия цепочки служебных слов и соединение пробелом — без изменений. Длина замены равна длине токена (каждый символ меняется на один), поэтому арифметика удаления и сдвиг курсора не меняются.

Для короткой команды терминала (`isTerminalCommand`) прочтение не строится: конверсия — всё слово, как сейчас.

Проактивный путь (два первых символа) не меняется: его сигналы — только буквы (`strongRussianSignals`, `strongEnglishSignals`), и ведущий символ из набора его не запускает.

Ручное исправление ⇧⇧ (`ManualFix.plan`) получает новые пары через таблицу автоматически и правил 1–2 не применяет: выделенное пользователь выбрал сам.

### 5. Побочные эффекты

- `foo:bar`, `"слово"`, `{x}` в английской раскладке читаются одним токеном, как сейчас `foo;bar`. Для детектора это нейтрально, а исправляемое слово перед `:` проверяется на следующей границе (пробеле), а не на самом `:`.
- В русской раскладке слово перед `:` (Shift+6) тоже проверяется на следующей границе. Результат тот же.

## Тесты

Юнит:

- `TextConverterTests`: шесть пар в обе стороны для `.pc` и `.apple`; «б» → `,` и «Б» → `<` одновременно (строчная пара не сломана); `~`/`|` по вариантам входят в `ambiguousLetterSymbols`; `shiftedLetterSymbols` — подмножество `ambiguousLetterSymbols`.
- `LanguageDetectorTests` для `wrongLayoutReading`: все строки таблицы примеров; хвост из нескольких символов набора (`ghbdtn"}` → «привет"}»); токен только из символов набора (`"::`) — `nil`; русское направление `цщкдвЖ` → `world:` через `prefix + toLatin(core) + suffix`; исключение выигрывает у LLR.

Замер — `scripts/eval-detector report` до и после изменения. Скоринг и пороги не меняются, но меняется, какие токены доходят до детектора (символы набора больше не рвут буфер). Сравнить пойманные и ложные срабатывания на всех наборах, включая частотно-взвешенные. Если ложных заметно больше — остановиться и разобрать до слияния.

Вручную: TextEdit — `"nj ` → «Это», `"ghbdtn" ` → `"привет"`, `ghbdtn: ` → «привет:»; Terminal — `БвшмЮ` в русской раскладке → `<div>`; `"hello"` и `foo:bar` в английской не трогаются.

## Вне рамок

- Цифровой ряд и прочая пунктуация русской раскладки (`№`, `?` на Shift+7 у Russian – PC и т.п.): не буквы, на детекцию не влияют.
- Применение правил хвоста и начала к выделению в ⇧⇧.
